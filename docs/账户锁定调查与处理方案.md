# 账户锁定调查与处理方案

状态: 调查完成，**前置取证已完成（2.5 节，假设已证实）**，方案待实施
关联: specs/功能规格/0041-lockscreen-probe.md（锁屏探针）；specs/项目规格/0001-architecture-invariants.md（模块边界）
代码: 待实施 —— 预计涉及 lib/pool.js / lib/session.js / lib/index.js / native/lockscreen/

## 一、问题陈述

用户在**锁屏后回到登录界面、输入正确密码**时，Windows 提示「引用的账户当前已被锁定，可能需要等待一段时间后才能登录」（状态码可能显示为 `0xc0000234`）。

用户的观察：该现象**从未出现过**，首次出现是在让 AI 操作浏览器期间锁屏，回来登录时发现账户被锁定。

用户的初始假设：锁屏状态下浏览器做了某些操作，触发了账户锁定。

## 二、调查结论

### 2.1 真正的机制

Chromium 内核浏览器（Chrome / Edge）在**每次浏览器进程启动时**，会用一个**空密码**调用 Windows 登录接口，目的是检测「这台电脑是否设置了开机密码」——因为密码管理员在展示已保存密码前要求验证 Windows 身份，而如果电脑本就没密码，这道确认就没有意义。

本机为该账户设置了密码，空密码必然认证失败，**Windows 于是在安全日志记一笔 4625（登录失败）事件**。

Chromium 把「已测试过」的结果记在本次 profile 的 `Local State` 文件里。问题在于：

- 插件每次 `browser_e2e_start` 都使用**全新的临时 profile**（Playwright 的 `chromium.launch()` 默认行为）
- `Local State` 随之丢失
- **每启动一次浏览器，就重新记录一次登录失败**

### 2.2 与账户锁定阈值的叠加

本机账户锁定策略（`net accounts` 实测）：

| 项 | 值 |
|---|---|
| Lockout threshold | 10 次 |
| Lockout observation window | 14 分钟 |
| Lockout duration | 15 分钟 |

AI 做浏览器自动化时会**频繁**启停浏览器（截图、验证页面、跑测试），14 分钟内累计 10 次失败非常容易。触发阈值后账户被锁定 15 分钟。

### 2.3 为什么「只在锁屏后才发现」

这一点解释了用户观察到的时序，也是排查困难的根源：

> **已登录状态下，账户被锁定不会把用户踢出当前会话。** 只有下一次需要重新认证时（锁屏后回到登录界面、重启、切换用户）才会撞上锁定状态。

因此「锁屏后出现」是**发现时刻**，不是**发生时刻**。锁屏与账户锁定之间没有因果关系，锁屏只是唯一会让用户看见该状态的场景。

这也意味着：**用户在使用电脑期间，失败次数同样在累积**，只是看不见。

### 2.4 触发链

```
AI 发起 browser_e2e_start
  → Playwright chromium.launch() 创建全新临时 profile
    → Chromium 启动时执行空密码探测（Local State 无标记）
      → Windows 记录一次 4625 登录失败
        → 反复启停累积
          → 超过 10 次 / 14 分钟
            → 账户锁定 15 分钟
              → 用户锁屏后回来登录时看到锁定提示
```

### 2.5 本机取证结果（2026-11-21 已完成证实）

本节原先标为「尚未证实」。**取证已完成，假设成立且比预期严重。** 管理员权限读取 Security 日志，窗口 30 天（2026-10-22 ~ 11-21），结果见 2.5.1 与 2.5.2。

#### 2.5.1 汇总数据

| 项 | 值 |
|---|---|
| 4625 总数 | 476 |
| **其中 `msedge.exe` 造成** | **127（26.7%）** |
| 另有一条独立来源（见 2.5.2） | 347（72.9%） |
| `svchost.exe` | 2 |
| 任意 14 分钟窗口内浏览器失败峰值 | **21 次**（阈值 10，超 2 倍） |
| 任意 60 分钟窗口峰值 | 34 次 |
| **4740 账户锁定事件** | **3 次**（11-18 两次、11-20 一次） |
| 锁定策略 | 阈值 10 / 观察窗 14 分钟 / 锁定 15 分钟 |

**结论：假设成立。** 浏览器启动确实在产生登录失败，且历史数据里存在真实的触发点。

时序佐证：11-20 单日 476 条中的 218 条；23:49–23:50 一分钟内 10 次（正好达阈值）；21:51 出现 `0xc0000234`（账户已锁定）记录，与 21:44:45 的 4740 事件吻合。

**与 2.3 节呼应**：这也证明「用户在使用电脑期间，失败次数同样在累积，只是看不见」——11-20 那天正是密集做浏览器自动化测试的日子。

#### 2.5.2 浏览器侧的字段特征（确认空密码探测）

\`\`\`
LogonProcessName            = Advapi
LogonType                   = 2          ← 交互式，非网络
AuthenticationPackageName   = Negotiate
ProcessName                 = C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe
Status / SubStatus          = 0xc000006d / 0xc000006a
FailureReason               = %%2313 (111/127)
IpAddress / IpPort          = - / -      ← 无网络字段
WorkstationName             = LENGDUAN-PC
\`\`\`

`LogonType=2` + `Advapi` + 无 IP/IPPort，说明是**进程内 `LogonUser` API 调用**；
`SubStatus=0xc000006a`（用户名正确、密码错误）正是空密码探测的特征。

与 2.1 节描述的机制完全一致：Chromium 启动时用空密码探测「本机是否设了密码」，失败即记 4625。

#### 2.5.3 另有一条独立来源（不属本方案）

347 条 4625 的 `ProcessName` 字段是字面量 `-`，与浏览器子集**在每个维度上都不同**：

| 维度 | 浏览器 127 条 | 空进程名 347 条 |
|---|---|---|
| `LogonType` | **2** 交互式 | **3** 网络 |
| 认证包 | **Negotiate** | **NTLM** |
| `IpAddress` | `-` 无网络 | **127.0.0.1** |
| `IpPort` | `-` | **真实源端口**（347 个互不相同） |
| `SubStatus` | **0xc000006a** | **0x0** |
| `FailureReason` | **%%2313** | **%%2304** |

**两个独立根因，不是同一件事。** 决定性证据是 `SubStatus` 完全不同：若同源不会如此。

第二条源是**走 NTLM over TCP 回环的真实网络认证**（`LogonType=3` + `NTLM` + `127.0.0.1` + 真实端口），
时间间隔在 **~90 秒与 ~240 秒之间交替**（17:33:10 → 17:34:42 → 17:38:43 → 17:40:12 → 17:44:11 …），
是**定时轮询**特征，非用户操作触发。按天分布 11-17:32 / 11-18:102 / 11-19:62 / 11-20:151，日均约 87 次。

**归属与本方案的关系**：

- 本方案**不覆盖**这条源，它来自企业安全软件一类常驻服务，通常有集中管控配置，不宜自行修改。
- 但它与浏览器源**计入同一套锁定计数器**，日均 87 次，会**让浏览器侧触发锁定的时间提前**。
- **即使浏览器侧归零，这条源仍可能单独把账户锁住。** 这是本方案效果的已知上限。

**候选进程**（按本机回环监听端口表）：`EndpointClientAgent`、`EndpointTrafficServer`、`EndpointInjectionFramework`、`SPELite`、`ztsmrtp`、`ztsmedr`、`SmartVPN`。
定位方法（尚未执行，按用户要求暂缓）：用 `IpPort` 与时序对 `Get-NetTCPConnection`，锁定具体进程。

**关于 `%%2304`**：`net helpmsg 2304` 无此消息文本，公开检索未命中其权威定义。
**本结论不依赖它**——`LogonType=3 + NTLM + 回环` 三项已足够定性。

## 三、关键 API 约束（实测）

这些约束直接决定了方案形态，均为本机实测结论。

### 3.1 chromium.launch() 不支持 userDataDir

```
$ node -e "chromium.launch({ userDataDir: '...' })"
Error: userDataDir option is not supported in browserType.launch.
       Use browserType.launchPersistentContext instead
```

**连通过 args 绕过也被显式拦截**：

```
$ chromium.launch({ args: ['--user-data-dir=C:/tmp/x'] })
Error: browserType.launch: Pass userDataDir parameter to
       'browserType.launchPersistentContext(userDataDir, options)'
       instead of specifying '--user-data-dir' argument
```

结论：**想控制 profile 位置，只能用 launchPersistentContext。**

### 3.2 launchPersistentContext 可以再分出隔离 context（关键可行性）

实测已验证：

```js
const ctx1 = await chromium.launchPersistentContext(dir, { channel: 'msedge', headless: true })
const browser = ctx1.browser()           // 能拿到 Browser 对象
const ctx2 = await browser.newContext()  // 可用
// browser.contexts().length === 2
```

**这保住了「共享实例 + 每会话隔离 context」的架构**：用 persistent context 作为**固定的 profile 宿主**（只为控制 `Local State` 位置），会话的隔离 context 仍由 `browser.newContext()` 创建。

### 3.3 Local State 会被 Chromium 改写

实测：预写 `password_manager.os_password_last_changed` 后重启浏览器，该字段被**覆盖**：

| 时机 | 值 |
|---|---|
| 预写 | `"9223372036854775807"` |
| 重启后 | `"13424837222064658"` |

**这不一定是坏事**：值被改写说明 Chromium 读取并处理了该字段，而不是忽略它。但意味着「预写值原样保留」不是可靠判据，**验证应该看 4625 事件是否消失，而不是看文件内容是否被保留**。

### 3.4 --disable-features 实际可用（原「未生效」结论已推翻）

**原结论是误判**。2026-11-21 用三组对照实测（Playwright 1.63 + 系统 Edge，读宿主真实进程命令行而非页面自报）：

| 场景 | 命令行里 `--disable-features` 开关数 | 我们的 feature 在不在 |
|---|---|---|
| 不传 `args` | **1**（只有 Playwright 默认 15 项） | 否 |
| `args` 传我们自己的 2 项 | **2**（默认一组 + 我们一组） | **在** |
| 传「默认 + 我们」合并后的完整清单 | **2** | 在，但默认清单重复了一份 |

主进程真实命令行（截断）——两组开关都在，顺序固定：

```
[...] --disable-features=AvoidUnnecessaryBeforeUnloadCheckSync,...,msEdgeUpdateLaunchServicesPreferredVersion   ← pos=489，len=336（Playwright 默认）
      --enable-features=CDPScreenshotNewSurface ...
      --disable-features=AutofillAiWalletPrivatePasses,AutofillAmbientAutofill                                 ← pos=1609，len=53（我们追加）
```

**机制（读 Playwright 源码确认）**：`node_modules/playwright-core/lib/coreBundle.js` 里

```js
const chromeArguments = [...chromiumSwitches()]   // :43336 / :43537  先放默认参数
...
chromeArguments.push(...args)                    // :43364 / :43567  再追加用户 args
```

`chromiumSwitches()` 内部会拼 `"--disable-features=" + disabledFeatures.join(",")`（:34871），
默认禁用 15 项。用户 `args` **追加在其后**，所以是两个**独立**开关，不是合并，也**不会被丢弃**。

**结论**：可以直接传 `--disable-features=...`，无需手工合并默认清单——
**手工合并反而会造出两个含默认项的重复开关**（上表第三行）。

**遗留不确定点（如实记录）**：Chromium 对重复开关取哪一个值，未在本机证实。
公开检索未命中 `base::CommandLine` 的权威说明（只找到 `command_line.h` 的 diff 页面）。
按 Chromium 通行行为推测「后者覆盖前者」，则我们的清单会**整体替换**默认 15 项——
但这会让 `DestroyProfileOnBrowserClose`、`HttpsUpgrades`、`PaintHolding` 等 Playwright 依赖的禁用项失效，可能影响插件既有行为。

**因此实施建议（步骤 6 采用）**：不直接追加裸清单，而是
`拼成「Playwright 默认 15 项 + 我们的 2 项」的单一开关**并放在最后**。
这样无论 Chromium 取首个还是末个，结果都一致——**契约不依赖这个未证实的规则**。

## 四、处理方案

按「从源头断绝 → 降低频率 → 减少暴露」三层设计，全部可独立开关。

### 第一层：从源头断绝（根治）

**1-A. 固定 profile 目录 + 预写 Local State**

- 在池启动浏览器前，创建一个稳定的 profile 目录（如 `~/.dsh/browser-e2e/browser-profile/`）
- 若 `Local State` 不存在或缺少 `password_manager` 段，写入：

```json
{
  "password_manager": {
    "os_password_blank": false,
    "os_password_last_changed": "9223372036854775807"
  }
}
```

- **必须合并已有内容，不能整体覆盖**（`Local State` 存有大量其他状态）
- `os_password_last_changed` **必须是字符串**，写成数字 Chromium 会判定格式非法并重新测试

**1-B. 启动参数**

```
--disable-features=AutofillAiWalletPrivatePasses,AutofillAmbientAutofill
```

Chrome 156+ 开始，自动填入功能会额外触发身份验证探测，这两个 feature 开关可以关掉。

**注意**：Chromium 只认**最后一个** `--disable-features`。若 Playwright 或其他地方已传，必须**合并成一个清单放在最后**，否则被覆盖。

### 第二层：降低频率（架构红利）

**2-A. 共享浏览器实例（用户正在实施的改造）**

现状是「每会话独立浏览器」，改造后是「共享实例 + 每会话隔离 context」。这份改造本身就大幅削减触发次数：

| 架构 | 每 N 次 start 的进程启动次数 | 4625 触发次数 |
|---|---|---|
| 现状：每会话独立浏览器 | N | **N** |
| 改造后：共享实例 | 1（池首次） | **1** |

**新建 context 不触发**：空密码探测是**浏览器进程启动时**的一次性任务，`browser.newContext()` 只是在已启动进程内开隔离存储分区，不启动新进程、不重跑初始化。

**2-B. 池级 profile 复用**

配合 1-A，池在 `POOL_IDLE_CLOSE_MS`（默认 120 秒）闲置后关闭浏览器，下次 `acquire` 重启时**复用同一 profile 目录**，`Local State` 标记仍在（即使值被改写，语义仍有效），不重新测试。

### 第三层：减少暴露（锁屏闸门）

**3-A. 锁屏检测保留，时机放在「真正拉起浏览器进程」处**

用户方案：锁屏检测保留，调用**放在启动无头浏览器时**，而非新建隔离 context 时。

**这个时机选择是正确的**，理由：

- 语义准确：危险动作是「拉起新浏览器进程」，不是「开 context」
- 开销合理：只在池首次启动时检测一次，复用路径完全跳过
- 与第二层改造自然契合

**位置建议**：`lib/pool.js` 的 `acquire()` 中**真正调用 `launchImpl` 的分支**（约 pool.js:110-118），而不是 `browser_e2e_start` 入口。后者在复用路径上也会执行，那时并没有新进程，检测纯属浪费。

**3-B. 锁屏时的行为**

用户方案：已锁屏时，用**预先准备好的 user data** 启动，绕过空密码检测。

这与 1-A 是同一件事的两个面——**「准备好的 user data」就是预写好 `Local State` 的 profile**。所以：

- 若 1-A 已生效（profile 里标记有效）→ 锁屏时启动也不会产生 4625，可以正常启动
- 若 1-A 未生效或 profile 被重建 → 锁屏时应**拒绝启动**并给出明确文案

**建议策略**：默认**尝试安全启动**（用预置 profile），仅当安全启动不可用时才拒绝。拒绝时文案要说明原因，而不是笼统报「浏览器尚未启动」。

### 3-C. 可选：失败次数熔断

若能在不读安全日志的前提下获得失败计数（如通过轻量探测），可在短时间内多次启动时主动退避。**当前不实现**——检测成本可能高于收益，且误判会干扰正常使用。

## 六、验证方法

### 6.1 前置取证（已完成，2026-11-21；方法保留供复现）

取证结果见 2.5 节。**复现命令如下**（需管理员权限，普通权限读 Security 日志会表现为「找不到事件」而非「拒绝访问」，容易误判成「没有失败」）。

```powershell
# 汇总：策略 + 4625 分类 + 14 分钟峰值 + 4740
pwsh -File .scratch\account-lock-forensics.ps1 -Days 30 -OutFile .scratch\forensics-result.txt

# 细分：区分「浏览器空密码探测」与「本地服务 NTLM 回环认证」
pwsh -File .scratch\account-lock-detail.ps1 -Days 30 -OutFile .scratch\detail-result.txt
```

`.scratch/` 已被 gitignore，这两个脚本不进仓库。等价的最小手工命令：

```powershell
# 4625 按进程分布
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4625;StartTime=(Get-Date).AddDays(-30)} |
  ForEach-Object { ([xml]$_.ToXml()).Event.EventData.Data | Where-Object Name -eq 'ProcessName' } |
  Group-Object '#text' | Sort-Object Count -Descending

# 4740 账户锁定
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4740} -MaxEvents 10 |
  Format-List TimeCreated, Message
```

**不要用 `$_.Properties[18].Value` 取进程名**：该索引随事件版本与系统语言漂移。改用 XML 的 `EventData.Data` 按 `Name` 取字段。

**空字段是字面量 `-` 而非空字符串**：判断时须 `$s -eq '-' -or $s -eq ''` 一起判，否则 `-not $v` 为假（`-` 是真值），会把空进程名的 347 条并进「其它已知进程」，得出相反结论。

**这一步是整个方案的前提**。若日志中不存在 `msedge.exe` 的 4625 记录，说明触发源是其他程序，需重新排查。

### 6.2 实施后验收

1. 记录实施前 24 小时内的 `msedge.exe` 4625 条数（基线）
2. 实施后跑同样的浏览器启停负载
3. 对比条数：**目标为 0**
4. 锁屏后回来登录，确认不再出现锁定提示

### 6.3 止血手段（非修复）

若需立刻缓解，可临时调高阈值：

```powershell
net accounts /lockoutthreshold:999
```

**这只是止血**：失败记录照常产生，只是不再触发锁定。安全性下降（削弱了防暴力破解保护），确认修复生效后应改回。

## 七、风险与限制

| 风险 | 说明 |
|---|---|
| 根因尚未在本机证实 | 方案基于公开报告与本机策略吻合，但缺本机 4625 证据 |
| Local State 结构属于 Chromium 内部实现 | 字段名与语义可能随版本变化，需要版本适配与降级 |
| 修改 profile 可能影响登录态 | 池的 profile 是插件自建临时目录，不碰用户真实 Edge profile；但若引入持久化目录，需明确其生命周期与清理策略 |
| --disable-features 可能影响页面行为 | 关掉自动填入相关 feature，若未来有测试用例依赖这些能力需重新评估 |
| 不解决非浏览器来源 | 若还有其他程序（如 VPN 客户端、映射驱动器）在产生失败登录，本方案不覆盖 |

**已知坑（抄脚本时注意）**：

- `H` 是 `Get-History` 的内置别名，不能用做函数名。
- PowerShell 7 的 `Group-Object` **不接受 `-ScriptBlock`**，改用哈希表手工累计。
- `@()` 数组字面量**不允许尾随逗号**。
- 反引号续行放在数组/哈希表字面量里容易与 `-f` 格式串冲突，改单行赋值。
