# 功能规格

一个功能点一份文件。写清「输入 → 行为 → 可验收的结果」，实现前先写，实现后同步更新。

写代码前先读本目录里与需求对应的文件；没有对应文件时，先补这一份再动手。

## 模板

新建 `NNNN-<slug>.md`（`NNNN` 从 `0001` 递增，`slug` 用小写英文短横线），内容按下面五节：

```markdown
# <功能点名称>

状态: 草稿 | 已确认 | 已实现
关联: specs/项目规格/0001-xxx.md（没有就写「无」）
代码: lib/xxx.js / client/index.js / tests/xxx.mjs

## 需求

要解决的问题，以及使用者能看到的收益。一两句。

## 行为

- 输入：参数名、类型、区间、缺省值、互斥关系。
- 输出：返回形状、写入位置、失败时的错误信息。
- 状态变化：会话 / 标签页 / 面板 / 浏览器进程分别变成什么样。

## 边界

- 非法输入、并发、超时、宿主缺服务时的表现。
- 明确不处理的场景。

## 验收

每条都要能被一次具体检查判定：跑哪个 `node tests/xxx.mjs`、命中哪个用例名、看到什么输出、
页面 / 面板 / 进程状态如何。写「它工作正常」不算验收。

- 命令与用例名必须真实存在（先读测试文件确认）。
- 不写死 PASS 总数：写「exit 0、无 FAIL」。要留历史实测数字时注明日期，并写明复跑以 exit code 为准。
```

## 过时表述的标记方式

规格与实现冲突时，**不要直接删掉旧说法**（读者需要知道「以前是什么」才能理解为什么要改）。按下面格式就地标记：

```markdown
> **[已过时 YYYY-MM-DD]** 旧说法原文，保留不删。
> 现在：新说法。变更原因：为什么改（一两句，能指到证据就指）。
> 详见 [0041-browser-pool.md](0041-browser-pool.md)「决策变更的原因」。
```

要求：

- 用引用块 `>` 与正文区分，一眼能看出哪段是旧的。
- 三段齐全：**旧说法**（原文保留）、**现在**（最新行为）、**变更原因**（不能只写「已更新」）。
- 同一处变更涉及多个文件时，只在最相关的那份写完整因果，其余写一句结论 + 链接，避免多处维护。

## 约定

- 一份文件只写一个功能点；相邻功能点在文内互相链接，不合并成一份。
- 行为变了就改对应文件；新增文件时同步在上面模板的「关联」里引用项目规格的相关条目。
- 验收标准写可执行的检查，不写主观描述。
- 全文定位实现一律写「文件 + 符号名」（函数 / 常量 / 类 / 导出名），不写行号。
- 「代码:」行只列真实参与该功能点的源文件与测试文件；构建产物（`lib/client.js`）算源文件
  `client/index.js` 的产物，不单独列。
